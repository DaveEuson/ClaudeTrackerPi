## Yoyu v1.11.0

**Linux gets a real package.** A `.deb` for Debian and Ubuntu, and an AppImage
for everything else. Companion only again; the firmware changes nothing but the
version it reports.

### Two ways to install on Linux

| | |
|---|---|
| **`.deb`** | `sudo apt install ./yoyu-companion_amd64.deb` |
| **AppImage** | `chmod +x` it and run it. No install, no root. |

The `.deb` puts `yoyu-companion` and `yoyu-companion-cli` on your path, adds a
menu entry with an icon, and removes cleanly with `apt remove yoyu-companion`.
It carries AppStream metadata, so a software centre shows it with a name and a
description rather than as a bare package id.

Both are built on Ubuntu 24.04 and want a glibc of roughly that vintage. On
something older, run the companion from source.

The plain `YoyuCompanion-linux` binary has not gone anywhere. If you liked
having one file you could put where you wanted, that is still the download at
the top of the setup page.

### Why Windows and macOS did not get one

Because it would not have helped, and on macOS it would have hurt.

v1.10.0 documented what unsigned downloads run into: SmartScreen on Windows,
Gatekeeper on macOS, and Defender occasionally quarantining the file outright.
Wrapping the same unsigned binary in an installer does not answer any of that.
A Windows setup program trips SmartScreen harder than a plain executable does,
because it asks for elevation and writes outside your profile. A macOS `.dmg`
is worse still: a quarantined unsigned application bundle is gated more
tightly than a bare binary, and the right-click-and-Open advice in the
troubleshooting guide stops working for it.

Linux has no equivalent gate, which is the whole reason it is the platform
worth packaging for today. Code signing is what unlocks the other two, and
that is a purchase rather than a piece of work.

### A packaged copy knows it is packaged

The companion learned to install itself in v1.10.0, and that would have gone
wrong here. Its idea of "installed" was a copy under your home directory, so a
companion installed with `apt` would still have offered **Install on this
computer**, copied `/usr/bin`'s binary into `~/.local`, and left you with two,
with the package manager updating the one you had stopped using.

It now recognises the directories a distribution owns, hides the offer, and
explains itself if you ask for it anyway:

```
This copy was installed by your package manager (/usr/bin/yoyu-companion-cli).
Copying it somewhere else would leave two, and the package manager would keep
updating the one you stopped using.
```

That refusal is checked on every build against a genuinely installed `.deb`,
rather than against the branch that is supposed to produce it.

AppImages needed the same care from the other direction. One runs from a
temporary mount that stops existing the moment the app quits, so installing
from inside an AppImage, or asking it to start at login, used to record a path
that had already gone. The real file is the one you downloaded, and that is
what gets copied now.

### Upgrading

**Boards can skip this one**, as they could v1.10.0. Nothing in the firmware
changed except the version it reports, so a board on v1.10.0 behaves exactly
like one on v1.11.0. Update it if you would rather the numbers matched.

On Linux, install whichever package suits you. Everywhere else, the companion
downloads are unchanged from v1.10.0, and an existing install upgrades in place
with `--install`.
