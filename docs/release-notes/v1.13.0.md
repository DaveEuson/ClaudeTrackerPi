## Yoyu v1.13.0

**A board flashed with the wrong firmware now says so.** Until this release it
had no way to, and the failure looked exactly like a device that would not turn
on.

### The failure this fixes

Both boards' images are validly signed, so nothing in the OTA signature check
can tell them apart. The setup page asks which board you have precisely because
that choice picks the image, and picking the wrong one flashes a working board
with firmware for the other panel.

What you get is the most confusing shape a fault can take. The board boots. It
joins your Wi-Fi. It serves its whole web interface and answers every API call
correctly. It just drives a display controller that is not physically present,
so the screen never lights. The LEDs on the back stay on throughout.

From the desk that is a dead device. From the network it is a healthy one.

This happened to a real board, and the thing that identified it was comparing
its permanent id against what it claimed to be:

```
id=85e050  board=lcd2       v1.9.1     <- before
id=85e050  board=amoled216  v1.12.0    <- after
```

Same board, different hardware according to its own firmware.

### How it detects it

The two boards use different I2C pins and different chips. The LCD board has a
CST816D at `0x15` on one pair of pins; the AMOLED has a CST9220, an AXP2101
power-management IC, an IMU, an RTC and an audio codec on another pair. Wrong
firmware brings up the wrong pins and finds an empty bus.

Rather than infer from that emptiness, each build goes and looks for the *other*
board's fingerprint: its I2C pins, and the chip that is always on them. Finding
the AMOLED's power-management IC where this board has no I2C at all is a
positive identification, not a guess. That matters, because an empty bus can
also mean a dead touch controller, which one of these boards is already known
to have.

The check only runs when nothing answered where the build expects its own
hardware, so a working board never executes any of it.

### Where it tells you

- **`/api/status` gains `hw_ok` and `hw_note`.** `false` means this firmware is
  on the wrong board, with a sentence saying which way round.
- **On serial at boot**, in a block that is hard to miss.
- **The companion prints it at startup** and when it finds such a board, in
  both the CLI and the tray.
- **The tray menu marks the board** and notifies once.

Firmware older than this sends neither field. Absent means "cannot tell", which
is treated as fine, so the companion never accuses a healthy older board.

### If you have one of these

**An over-the-air update will not fix it.** The running firmware decides which
release asset to fetch, so a board that believes it is the other board keeps
downloading the other board's image forever. It has to be re-flashed over USB
from the setup page, choosing the board you actually have.

The [troubleshooting guide](../TROUBLESHOOTING.md#the-board-will-not-turn-on-or-the-screen-stays-dark)
has the full sequence, including how to tell which board you are holding.

### Upgrading

Over the air from `/update`, or re-flash from the setup page. Wi-Fi, login,
settings and history all survive.

Unlike the last three releases, this one does change the firmware, so it is
worth taking. It cannot repair a board that is already on the wrong image,
since that board is running the other build; it is what stops the next one
being a mystery.
